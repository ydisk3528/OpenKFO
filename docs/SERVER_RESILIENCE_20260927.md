# 服务器等待与恢复改进（2026-09-27，本地候选）

未部署线上，未替换或重启本地正在运行的服务。玩家数据库、商城和 OSS 未修改。

## 已实现

- MySQL 连接、读、写默认上限各 5 秒，保留更短的显式配置。58 个业务事务入口改用 BeginTx 的 15 秒上下文，包含等待连接池和事务生命周期；退出时取消上下文，维持原有事务、回执和回滚行为。
- 存储操作等待超过 2 秒会输出正在等待的账号 UID、房间、连接池占用及等待计数，不记录凭据或 SQL 内容。
- 原先只保留 5 秒的 PVE 报告改为本局内保留。5 秒后向房间发送一次等待提示，重检频率降为每秒；完整进度到达后仍用原校验和事务结算。换局、换房主、退出后旧回调失效。
- 原生 UDP 使用独立有界发送队列和发送任务，不再排在慢 TCP 写入之后。UDP 不可用时保留原 TCP 回退路径；仍限制队列数量及总字节，溢出记录明确原因，不改战斗协议。

## 仍有边界

- 全局 ioPaused 业务等待机制仍在，共享状态写操作仍可能相互等待。没有宣称彻底完成账号/房间隔离，也没有线上性能收益证据。
- 非事务查询尚未全部改为带上下文的 QueryContext；驱动读写超时不等于完整的连接池等待上限。
- 若客户端永远不补齐进度，不能凭空判定通关或发奖。报告会留在当前局等待，没有自动编造缺失协议。
- UDP 不可用时回退 TCP，仍受 TCP 链路延迟影响；不改变客户端原有跨传输顺序语义。
- 当前构建包含工作区既有服务器改动；不要仅因候选构建成功而自动部署。后续先做相同负载的等待时间、尾延迟和吞吐对照，再决定进一步拆锁。
