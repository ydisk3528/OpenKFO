## 执行与安全

- game/horn.go：独立 HornManager，在线索引按 UID 分 32 片，并按频道索引。
- 入站只解析、限频和提交任务；数据库/文字审核在独立 FIFO 工作者执行，不等待战斗请求处理锁。
- 每账号最多一个未完成请求，成功/失败后可再发送，间隔至少 2 秒。原请求没有请求流水号，因此不能把跨重连的相同文本自动认作重复。
- 最多 128 个排队请求，队满直接拒绝且不扣卡。空闲时工作者退出。
- 实际扣卡在 MySQL 账号行锁事务内完成，只允许类型 71、编号 713001、有效且数量足够的道具；多堆叠先完整计算，不足时不修改。
- 卡用完保留数据库实例编号，标记退役，并发送 2162 从客户端移除；未用完发送 2161 数量更新。
- 请求中的 UID/昵称不可信，广播使用服务器认证身份。
- 消息只编码一次。每批最多 128 个接收者，只在短暂读锁下向现有连接队列非阻塞投递，网络仍由原连接写循环处理。
- 为战斗/控制消息保留队列空间；离线/切换频道/拥堵连接会跳过，不强制踢出慢接收者，不向重连玩家补发旧消息。
- horn_events 与扣卡在同一事务提交，包含流水、账号、类型、消耗、正文和投递统计。
- status=pending 表示扣卡已提交、广播结果未确认；异常退出时留待核对，不自动重发或再次扣卡。status=dispatched/queued 仅代表进入连接发送队列，不代表客户端显示确认。
