## 参考与原客户端核对

参考仓库已 fast-forward 到 47b0740（2026-09-23 22:02:30）。其 pve.py decode 识别 20406 长度，但 lifecycle 先限制 owner，且没有确认转发分支，不能直接照抄解决多人情况。

对当前 gfxz.dat 静态反汇编：

- 943B60：主控收集非主控、非旁观玩家槽位位图，与每只待接入怪物的 +B4 容器确认位图比较；相等才调用 943960 接入加载结果。
- 非主控加载完成路径 943D43..943D61：把怪物标识放入 +39，发 20406/47。
- 827FC0：从公共头 sender 查玩家槽位，从 +39 读 64 位怪物标识，调用模式虚表 +120。
- 模式10函数 940040：为对应怪物设置 `1 << senderSlot` 确认位。模式21的 938EF0 同样设置位图。

因此确认丢失会卡住主控的怪物接入屏障；单人所需远端位图为零，不受这个漏项影响。

## 修改及边界

pve_loaded.go 只接受当前战斗中已认证的非旁观玩家、精确长度/公共头、当前已登记的存活怪物，保留原包转发给主控。按玩家和怪物去重；怪物标识复用时，现有创建流程清除去重状态。不能拿队员的计数与主控创建计数比较，因为来自不同客户端。

这不伪造确认，不放开任意怪物生成，不修改客户端或奖励。

验证：game/protocol 测试通过，包括两种 PVE 模式、正常确认、重复、未知/已移除实体、伪造发送者、坏头/长度、旁观及非战斗状态。Linux amd64 服务端构建通过。尚未部署；当前在线游戏未被重启，真实多人活动仍需部署后复测。
